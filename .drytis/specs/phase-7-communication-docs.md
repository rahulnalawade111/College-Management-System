# Phase 7 — Notices, events, notifications, documents

## Goal
Communication & documents: targeted notices, events with student registration, in-app
notifications with read management, secure student document management with verification.

## Files
- backend V8: notices, events, event_registrations, notifications, documents (+ seed
  notices/events).
- Notices: CRUD (admin), targeting by role/department/course (+ PUBLIC), students/parents
  see only relevant+non-expired notices (backend filter, not client-side), attachment upload.
- Events: CRUD, registration_required flag, student register/unregister (UQ event+student),
  admin sees attendee list; upcoming events feed on public site & dashboards.
- Notifications: generated by system events (fee payment, result published, notice for your
  target, event reminder); APIs: GET /api/notifications (mine, paged, unread count),
  PATCH /{id}/read, POST /mark-all-read, DELETE /{id}; bell icon with unread badge in the
  dashboard header.
- Documents: upload (type validation, ≤5MB default from settings, filename sanitization),
  private storage via FileStorageService, served only through authorized
  GET /api/files/{documentId}; student sees own, admin sees all, faculty sees students of
  own subjects; admin verify/reject with verification_status + verified_by; profile
  document lists in student profile page.
- FileSecurity: block executable extensions (exe/sh/bat/js…), whitelist jpg/png/pdf/doc(x)/xls(x).

## Acceptance criteria
- [ ] A notice targeted to STUDENT + Computer Science department appears for such students
      but not for a Commerce student or a faculty account.
- [ ] Expired notices disappear from lists automatically.
- [ ] Student can register for a registration-required event and appears in the admin
      attendee list; duplicate registration is rejected.
- [ ] Unread notification badge count matches backend unread count; mark-all-read clears it.
- [ ] Uploading a 10MB file or an .exe is rejected with a clear message.
- [ ] A document URL cannot be opened by a different logged-in student or anonymous user
      (authorization enforced on the file endpoint).
- [ ] Admin verification updates the document status shown in the student's profile.

## Tests
Notice targeting filter, event registration dedup, notification read lifecycle, file type/
size validation, document access authorization matrix.

## Edge cases
Notice with multiple targets, event without registration requirement, concurrent
notification reads, file with double extension, unicode filenames.
